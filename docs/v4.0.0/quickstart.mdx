<Callout type="warning" title="Experimental release">
Aqua Protocol v4 is under active development. The published components — <code>aqua-rs-sdk-core</code> and <code>aqua-template-registry</code> — are an early community release with a deliberately limited functionality scope. Version numbers have not yet been increased, backward compatibility is not yet provided, and breaking changes are expected and may occur without notice. The full <code>aqua-rs-sdk</code>, which extends this core, is scheduled for a later publication. For production use today, refer to the stable [v3 documentation](/docs/v3.0.2/introduction).
</Callout>

This guide goes from an empty directory to a verified Aqua tree in one small Rust program: create a genesis revision for a piece of content, sign it with an Ed25519 key, and run the full verification pipeline.

<Steps>
  <Step title="Prerequisites">
    - A stable [Rust toolchain](https://rustup.rs) (`rustc` and `cargo`; the crate uses edition 2021)
    - `git` — cargo fetches the SDK directly from GitHub
  </Step>

  <Step title="Create a project and add dependencies">
    ```bash
    cargo new aqua-hello
    cd aqua-hello
    ```

    Add the dependencies to `Cargo.toml`:

    ```toml
    [dependencies]
    aqua-rs-sdk-core = { git = "https://github.com/inblockio/aqua-rs-sdk-core" }
    tokio = { version = "1", features = ["full"] }
    hex = "0.4"
    ```

    `aqua-rs-sdk-core` is not on crates.io yet (publication is planned), so the dependency points at the Git repository. `tokio` provides the async runtime for the signing and verification calls; `hex` decodes a signing key supplied as hex.
  </Step>

  <Step title="Write the program">
    Replace `src/main.rs` with:

    ```rust
    use aqua_rs_sdk_core::schema::{AquaTreeWrapper, FileData, SigningCredentials};
    use aqua_rs_sdk_core::Aquafier;
    use std::path::PathBuf;

    #[tokio::main]
    async fn main() -> Result<(), Box<dyn std::error::Error>> {
        let aquafier = Aquafier::new();

        // 1. Create a genesis revision for some content.
        let file = FileData::new(
            "hello.txt".to_string(),
            b"hello world".to_vec(),
            PathBuf::from("hello.txt"),
        );
        let tree = aquafier.create_genesis_revision(file.clone(), None)?;

        // 2. Sign it with an Ed25519 key (a did:key identity).
        //    The fallback below is a fixed demo secret (the bytes 1..=32) so
        //    that this example runs out of the box. NEVER use a hard-coded or
        //    predictable key in production: generate a fresh one with
        //    aqua_rs_sdk_core::generate_ed25519() and keep it out of your
        //    source code.
        let secret: Vec<u8> = std::env::var("MY_ED25519_SECRET_HEX")
            .map(|h| hex::decode(h).expect("MY_ED25519_SECRET_HEX must be hex"))
            .unwrap_or_else(|_| (1..=32).collect());
        let creds = SigningCredentials::Did { did_key: secret };
        let signed = aquafier
            .sign_aqua_tree(AquaTreeWrapper::new(tree, None, None), &creds, None, None)
            .await?;

        // 3. Verify the full pipeline: structure, hashes, schema, signature.
        let result = aquafier
            .verify_aqua_tree(
                AquaTreeWrapper::new(signed.aqua_tree, Some(file.clone()), None),
                vec![file],
            )
            .await?;

        println!("verified: {}", result.is_verified());
        Ok(())
    }
    ```

    The three calls mirror the protocol lifecycle: `create_genesis_revision` builds a new tree, `sign_aqua_tree` appends a signature revision attesting to the tree's tip, and `verify_aqua_tree` runs the complete verification pipeline over the result.
  </Step>

  <Step title="Run it">
    ```bash
    cargo run
    ```

    The first build fetches and compiles the SDK from GitHub. The program prints:

    ```text
    verified: true
    ```

    `true` means the tree verified — `is_verified()` accepts both the `verified` and `verified_with_warnings` outcomes, and this program produces no warnings. Every check passed — structural validity, recomputed revision hashes, payload schema conformance, file content (checked by size and content hash, never by filename), and the Ed25519 signature — under the default `strict` verification policy.

    The tree itself is a plain JSON document. The example below is abridged from one of the SDK's deterministic test fixtures (`sign_did_example.aqua.json`) and shows the same three revision kinds your program produced — a genesis anchor, a typed object revision, and a signature revision (hashes shortened with `…` for readability):


    Two differences in your run. First, the SDK hashes object revisions with the `tree` method by default, so your object revision also carries a `leaves` array of per-field digests — the fixture above was created with the `scalar` method, which has no `leaves`. Second, the fixture's signature revision targets the genesis anchor (its `previous_revision` names the anchor), while your program signed the tree's tip, so your signature's `previous_revision` names the object revision. To inspect your own tree, add `serde_json = "1"` to the dependencies and print `serde_json::to_string_pretty(&signed.aqua_tree)?` before the verification call.
  </Step>

  <Step title="What just happened">
    - **A genesis anchor declared the tree's type.** `create_genesis_revision` built a two-revision tree: a genesis anchor whose `structural_links` name the built-in `file` template, followed by an object revision typed by that template. The object's `payloads` records the content hash, size, and MIME type of `hello.txt` — not the content itself.
    - **A signature revision attested to a revision hash.** `sign_aqua_tree` appended a signature revision branching off the tree's tip — in your program, the object revision. Its `signer` is the `did:key` identity derived from the Ed25519 key, and what it signs includes the target's revision hash — so the signature covers the target's entire content indirectly.
    - **Every link is a multihash.** Each revision is stored under the hash of its own canonical form, rendered as `0x` + 68 hex characters. `previous_revision` and `revision_type` are such links, and the hash algorithm (SHA3-256 here, codec `0x16`) travels inside the multihash — revisions carry no algorithm field.
    - **`revision_type` is a template multihash, never a keyword.** The anchor names the `anchor_template`, the object names the `file` template, and the signature names the `signature_ed25519` template. Types are content hashes, not strings.
    - **Verification recomputed everything.** `verify_aqua_tree` resolved the anchor's structural links, recomputed every revision hash against its map key, validated the object's payload against the `file` template's JSON Schema, checked the file content by size and hash, and cryptographically verified the signature — failing closed on any mismatch.
  </Step>

## Troubleshooting

<Accordion>
  <AccordionItem title="cargo cannot fetch the git dependency">
    **Symptom:** `failed to get 'aqua-rs-sdk-core'` or `failed to load source for dependency` during `cargo build`.

    1. Ensure `git` is installed and on your `PATH` — cargo shells out to it for git dependencies.
    2. Check network access to `github.com` (proxies and offline mode both surface as fetch failures).
    3. Use the `Cargo.toml` git line shown above. `cargo add aqua-rs-sdk-core` does not work: it queries crates.io, where the crate is not yet published.
  </AccordionItem>

  <AccordionItem title="error: `main` function is not allowed to be `async`">
    The program needs an async runtime. Two things must both be present:

    1. `tokio = { version = "1", features = ["full"] }` in `Cargo.toml` (the `macros` and `rt-multi-thread` features it enables are the required minimum).
    2. The `#[tokio::main]` attribute directly above `async fn main`.
  </AccordionItem>

  <AccordionItem title="edition or toolchain errors">
    **Symptom:** `feature 'edition2021' is required` or parse errors inside the SDK's dependencies.

    Your toolchain is too old. The crate uses Rust edition 2021; update with `rustup update stable` and confirm with `cargo --version`. If a stale build cache persists after updating, run `cargo clean` and rebuild.
  </AccordionItem>
</Accordion>
